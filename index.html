Storage Engine

“เก็บข้อมูลอย่างไร”

  • กลไกระดับล่างที่อ่าน/เขียนข้อมูลลงดิสก์
  • กำหนดการทำธุรกรรม การล็อก ดัชนี และการกู้คืน
  • เลือกได้ รายตาราง

View

“มองข้อมูลอย่างไร”

  • ตารางเสมือนจากคำสั่ง SELECT ที่บันทึกไว้
  • ซ่อนความซับซ้อนของ JOIN และจำกัดสิทธิ์การมองเห็น
  • ไม่เก็บข้อมูลซ้ำ

Routine

“ประมวลผลอย่างไร”

  • Stored Procedure และ Stored Function
  • รวมตรรกะธุรกิจไว้ในฝั่งเซิร์ฟเวอร์
  • เรียกซ้ำได้จากทุกแอปพลิเคชัน

Storage Engine เลือกประสิทธิภาพ/ความปลอดภัย · View เลือกมุมมอง · Routine เลือกตรรกะ

1 · Storage Engineตำแหน่งของ Storage Engine ในสถาปัตยกรรมฐานข้อมูล

Connection Layer — รับการเชื่อมต่อ, ตรวจสิทธิ์, จัดการ thread
SQL Layer — Parser, Optimizer, Cache, ฟังก์ชัน, View, Routine
Pluggable Storage Engine API — ช่องเชื่อมมาตรฐาน
Engine: InnoDB · MyISAM · MEMORY · ARCHIVE · CSV · NDB ... → ไฟล์บนดิสก์/หน่วยความจำ

หลักการสำคัญ

  • SQL Layer เหมือนกันทุกตาราง แต่ วิธีเก็บและค้นหาข้อมูลต่างกันตาม Engine
  • ตารางเดียวกัน = Engine เดียว แต่ฐานข้อมูลเดียวผสมหลาย Engine ได้
  • ตรวจดู: SHOW ENGINES;
  • ค่าเริ่มต้นของระบบในปัจจุบันคือ InnoDB
  • สิ่งที่ Engine กำหนด: ACID, ระดับการล็อก, Foreign Key, ชนิดดัชนี, การกู้คืนหลังล่ม, รูปแบบไฟล์

1 · Storage Engineเปรียบเทียบ Engine ที่ใช้บ่อย

EngineTransaction / FKการล็อกจุดเด่นข้อจำกัด
InnoDBรองรับ ACID + FKRow-level + MVCCกู้คืนหลังล่มได้ (redo log), Clustered Index, FULLTEXT, ทำงานพร้อมกันสูงกินพื้นที่/หน่วยความจำกว่า, COUNT(*) ช้ากว่า MyISAM
MyISAMไม่รองรับTable-levelโครงสร้างเรียบง่าย อ่านเร็ว คัดลอกไฟล์ย้ายง่ายไม่ crash-safe, เขียนพร้อมกันได้ต่ำ, ไม่มี FK — ปัจจุบันไม่แนะนำ
MEMORYไม่รองรับTable-levelเก็บใน RAM เร็วมาก, Hash indexข้อมูลหายเมื่อรีสตาร์ท, ไม่รองรับ TEXT/BLOB
ARCHIVEไม่รองรับRow-levelบีบอัดสูง เหมาะกับ logINSERT/SELECT เท่านั้น แก้ไข/ลบไม่ได้, ดัชนีจำกัด
CSVไม่รองรับTable-levelเป็นไฟล์ .CSV เปิดใน Excel ได้ทันทีไม่มีดัชนี, ห้ามมีคอลัมน์ NULL

Engine อื่นที่ควรรู้: BLACKHOLE (ทิ้งข้อมูล ใช้ทำ replication relay), FEDERATED (เข้าถึงตารางบนเซิร์ฟเวอร์อื่น), NDB (Cluster)

1 · Storage Engineการเลือกและการใช้งาน

-- ระบุ Engine ตอนสร้างตาราง
CREATE TABLE orders (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  customer_id INT NOT NULL,
  total       DECIMAL(10,2),
  FOREIGN KEY (customer_id)
    REFERENCES customers(id)
) ENGINE=InnoDB;

-- ตาราง log ที่เขียนอย่างเดียว
CREATE TABLE access_log (
  at DATETIME, url VARCHAR(255)
) ENGINE=ARCHIVE;

-- ดู / เปลี่ยน Engine
SHOW ENGINES;
SHOW TABLE STATUS LIKE 'orders';
ALTER TABLE t ENGINE=InnoDB;

แนวทางเลือกใช้

  • ระบบธุรกรรมทั่วไป (ร้านค้า, ธนาคาร, ERP) → InnoDB
  • ข้อมูลชั่วคราว/แคชที่สร้างใหม่ได้ → MEMORY
  • Log/เก็บถาวรปริมาณมาก → ARCHIVE
  • แลกเปลี่ยนไฟล์กับโปรแกรมอื่น → CSV

ข้อควรระวัง

  • ALTER ... ENGINE สร้างตารางใหม่ ล็อกนานกับตารางใหญ่
  • ผสมหลาย Engine ใน transaction เดียว ย้อนกลับ (ROLLBACK) ได้ไม่ครบ

2 · ViewView คืออะไร และใช้อย่างไร

หลักการสำคัญ

  • View = คำสั่ง SELECT ที่ตั้งชื่อไว้ เรียกใช้เหมือนตาราง
  • ไม่เก็บข้อมูลเอง ทุกครั้งที่ query จะอ่านจากตารางต้นทางเสมอ (ไม่มี Materialized View ในตัว)
  • ควบคุมสิทธิ์ได้รายคอลัมน์ผ่าน GRANT SELECT ON view
  • ALGORITHM: MERGE (รวมเข้า query หลัก เร็ว), TEMPTABLE (สร้างตารางชั่วคราวก่อน), UNDEFINED

ตัวอย่างการใช้

  • รายงานยอดขายที่ JOIN หลายตาราง
  • ซ่อนคอลัมน์ลับ (เช่น เงินเดือน, รหัสผ่าน)
  • ให้แอปเก่าเห็นโครงสร้างเดิมหลังปรับ schema
CREATE OR REPLACE VIEW v_customer_sales AS
SELECT c.id, c.name,
       COUNT(o.id)  AS orders,
       SUM(o.total) AS revenue
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

-- ใช้งานเหมือนตารางปกติ
SELECT * FROM v_customer_sales
WHERE revenue > 10000;

-- View แบบอัปเดตได้ + กันข้อมูลหลุดเงื่อนไข
CREATE VIEW v_active_users AS
SELECT id, name, status FROM users
WHERE status = 'active'
WITH CHECK OPTION;

2 · Viewจุดเด่น ข้อจำกัด และการนำไปใช้

จุดเด่น

  • ความง่าย — ซ่อน JOIN ซับซ้อนไว้หลังชื่อเดียว
  • ความปลอดภัย — เปิดเฉพาะแถว/คอลัมน์ที่อนุญาต
  • ใช้ซ้ำ — แก้นิยามที่เดียว ทุกแอปได้ผลตรงกัน
  • อิสระจาก schema — ปรับตารางเบื้องหลังได้โดยไม่กระทบผู้ใช้
  • SQL SECURITY DEFINER | INVOKER กำหนดว่าใช้สิทธิ์ของใคร

ข้อจำกัด

  • สร้างดัชนีบน View โดยตรงไม่ได้ ต้องพึ่งดัชนีของตารางจริง
  • View ซ้อน View หลายชั้น ทำให้ optimizer ทำงานยากและช้า
  • อัปเดตผ่าน View ได้เฉพาะ กรณีแถวใน View ตรงกับแถวในตารางแบบ 1:1 — ห้ามมี GROUP BY, DISTINCT, UNION, aggregate
  • ไม่รองรับ trigger บน View
  • ถ้าตารางต้นทางเปลี่ยนชื่อ/ลบคอลัมน์ View จะใช้ไม่ได้ (ตรวจด้วย CHECK TABLE)

การนำไปใช้

  • Reporting / Dashboard / BI
  • Data mart ชั้นอ่านอย่างเดียว
  • จำกัดสิทธิ์ผู้ใช้ฝ่ายต่าง ๆ
  • ชั้น compatibility ตอนย้ายระบบ
  • เคล็ดลับ: ตั้งชื่อนำหน้า v_, หลีกเลี่ยง SELECT * ในนิยาม, ใช้ EXPLAIN ตรวจแผนการทำงาน

3 · RoutineStored Procedure กับ Stored Function

หัวข้อStored ProcedureStored Function
การเรียกใช้CALL sp_name(...) เรียกเป็นคำสั่งเดี่ยวใช้ในนิพจน์ เช่น SELECT fn(col), WHERE
ค่าที่ส่งกลับไม่จำเป็นต้องมี ส่งผ่านพารามิเตอร์ IN / OUT / INOUT หรือ result set ได้หลายชุดต้องคืนค่าเดียว (RETURNS) ชนิดข้อมูลเดียว
งานที่ทำได้INSERT/UPDATE/DELETE, START TRANSACTION / COMMIT, SQL แบบ dynamic (PREPARE)คำนวณ/แปลงค่า; ห้ามคืน result set และห้ามสั่ง COMMIT/ROLLBACK
เหมาะกับกระบวนการทางธุรกิจหลายขั้นตอน, งานแบตช์, ย้ายข้อมูลสูตรคำนวณที่ใช้ซ้ำ เช่น ภาษี ส่วนลด จัดรูปแบบข้อความ
องค์ประกอบร่วมDECLARE ตัวแปร · IF / CASE · LOOP / WHILE / REPEAT · Cursor · Handler (DECLARE ... HANDLER) สำหรับจัดการข้อผิดพลาด

หลักการสำคัญ

ตรรกะถูก คอมไพล์เก็บไว้ในฐานข้อมูล ส่งแค่ชื่อกับพารามิเตอร์ผ่านเครือข่าย ลดการสื่อสารไป-กลับ และกำหนดสิทธิ์ EXECUTE แยกจากสิทธิ์ของตารางได้

3 · Routineตัวอย่างโค้ด: สั่งซื้อสินค้าอย่างปลอดภัย + คำนวณ VAT

DELIMITER //
CREATE PROCEDURE sp_place_order(
  IN p_cust INT, IN p_amt DECIMAL(10,2),
  OUT p_id BIGINT)
BEGIN
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK; RESIGNAL;
  END;
  START TRANSACTION;
  INSERT INTO orders(customer_id, total)
    VALUES (p_cust, p_amt);
  SET p_id = LAST_INSERT_ID();
  COMMIT;
END //

CREATE FUNCTION fn_vat(p_amt DECIMAL(10,2))
RETURNS DECIMAL(10,2) DETERMINISTIC
RETURN ROUND(p_amt * 0.07, 2) //
DELIMITER ;
-- เรียกใช้
CALL sp_place_order(1, 1500.00, @new_id);
SELECT @new_id;

SELECT id, total, fn_vat(total) AS vat
FROM orders;

SHOW PROCEDURE STATUS WHERE Db = 'shop';
DROP PROCEDURE IF EXISTS sp_place_order;

จุดที่ควรสังเกต

  • HANDLER + ROLLBACK ทำให้ทั้งชุดคำสั่งสำเร็จหรือย้อนกลับพร้อมกัน
  • DELIMITER ใช้เฉพาะโปรแกรมไคลเอนต์แบบบรรทัดคำสั่ง เพื่อให้เครื่องหมาย ; ภายในไม่ตัดคำสั่ง
  • DETERMINISTIC ช่วยให้ผลลัพธ์คาดเดาได้

3 · Routineจุดเด่น ข้อจำกัด และการนำไปใช้

จุดเด่น

  • ลด network round-trip — หลายคำสั่งรวมเป็นการเรียกครั้งเดียว
  • ตรรกะรวมศูนย์ — แอปหลายภาษา/หลายระบบใช้กฎเดียวกัน
  • ปลอดภัย — ให้สิทธิ์ EXECUTE โดยไม่เปิดตารางตรง ๆ, ช่วยลดความเสี่ยง SQL Injection เมื่อส่งค่าเป็นพารามิเตอร์
  • ความสอดคล้องของข้อมูล — รวมธุรกรรมไว้จุดเดียว

ข้อจำกัด

  • Debug ยาก ไม่มี debugger ในตัว และเครื่องมือทดสอบจำกัด
  • จัดการเวอร์ชันยาก ต้องเก็บสคริปต์ใน Git/Migration
  • ภาษา SQL/PSM ต่างกันในแต่ละ DBMS ทำให้ย้ายระบบยาก
  • ภาระงานย้ายมาอยู่ที่ DB ซึ่งขยายขนาดยากกว่าเซิร์ฟเวอร์แอป
  • เปิด binary log ต้องตั้ง DETERMINISTIC หรือ log_bin_trust_function_creators
  • Function ที่ใช้ใน WHERE ทำให้ดัชนีใช้ไม่ได้

การนำไปใช้

  • กระบวนการชำระเงิน/ตัดสต็อก/โอนเงิน
  • งานแบตช์ปิดยอดรายวัน-เดือน
  • ตรวจสอบและแปลงข้อมูลก่อนบันทึก
  • สูตรคำนวณกลางที่ใช้ในรายงาน
  • แนวปฏิบัติ: ตั้งชื่อ sp_ / fn_, ใส่ Handler ทุกครั้ง, ไม่ใส่ตรรกะที่เปลี่ยนบ่อยไว้ใน DB
